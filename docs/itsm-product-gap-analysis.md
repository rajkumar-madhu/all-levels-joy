# WeCrew ITSM: product comparison and implementation

Assessment: 27–28 September 2026. Scope: this repository, current vendor documentation, and local validation. Vendor descriptions establish a capability benchmark; they are not independent product rankings or claims of equivalent implementation.

## Product direction

Develop WeCrew into an accountable service-operations workspace. The repository already covers incidents, requests/catalog, changes, approvals, problems, major incidents, knowledge, assets/CMDB, and an assistant. Its largest gap is the reliability and depth of the workflows connecting those modules. More module names or decorative dashboards would not close that gap.

This delivery strengthens incident operations and the shared B2B interface, then closes the identified core access, privacy, approval-transaction, and audit-integrity gaps in code. Enterprise readiness still requires controlled rollout, historical access review, organization selection, operational integrations, and the remaining product depth below.

## Delivered behavior and code

- `src/lib/incident-queue.ts`: validated queue and URL contracts; escaped PostgREST search values. Search treats `%`, `_`, and `*` as separators rather than wildcard syntax.
- `src/lib/incident-queue.server.ts`: organization-scoped queries using the authenticated caller's Supabase client. Counts use exact HEAD requests. Filters apply before pagination; individual record retrieval is independent of queue membership.
- `src/lib/incident-queue.functions.ts`: authenticated server entry points. The existing fixed organization model is retained and remains a known limitation.
- `src/components/incident-workbench.tsx`: queue summary, accessible controls, record table, recoverable error and empty states, stale-page recovery, polling disclosure.
- `src/routes/_authenticated/incidents.tsx`: complete queue-to-record workflow, focus-managed detail panel, assignment actions, allowed transitions, cancellation confirmation, activity and resolution evidence. Record versions remain stable until explicit refresh/update to avoid silently replacing an in-progress edit.
- `src/lib/incident-workflow.ts` and `src/lib/itsm.functions.ts`: pure workflow validation and server persistence with an `expectedUpdatedAt` token.
- `drizzle/migrations/0004_enforce_incident_workflow.sql`: applies lifecycle invariants and protected-field permissions to direct Supabase writes as well as application actions. Historical rows are not rewritten or given invented evidence.
- `src/lib/problem.functions.ts`: stops resolving linked incidents implicitly when the command bridge is resolved.
- `src/lib/itsm-shared.ts` and `src/components/status-badge.tsx`: accurate SLA states; cancelled records are not labeled active breaches in the new workbench.
- `drizzle/migrations/0005_workspace_access_privacy.sql`: active membership bootstrap and parent-aware RLS for records, notes, attachments, Storage and supporting modules.
- `drizzle/migrations/0006_atomic_approvals.sql` and `src/lib/approval.functions.ts`: transactional request/change creation, designated approval decisions, immutable submitted scope and lifecycle gates.
- `drizzle/migrations/0007_transactional_audit.sql`: immutable structured audit for core records, committed or rolled back with the originating mutation.
- `tests/e2e/`: repeatable real local Auth/REST/Storage/browser verification with temporary identities and test-stack cleanup.
- Shared design details: [ITSM design system](./itsm-design-system.md).

## Lifecycle contract

| From        | Allowed destination states                      |
| ----------- | ----------------------------------------------- |
| New         | Open, in progress, pending, resolved, cancelled |
| Open        | In progress, pending, resolved, cancelled       |
| In progress | Open, pending, resolved, cancelled              |
| Pending     | Open, in progress, resolved, cancelled          |
| Resolved    | Closed, open (reopen)                           |
| Closed      | Open (reopen)                                   |
| Cancelled   | None                                            |

Same-state metadata updates are allowed. Pending requires a recognized hold reason. Resolution requires nonblank notes and a recognized close code. Closing preserves the original resolution timestamp. Reopening clears previous completion evidence and increments the counter once. The incident must be refreshed before retrying a stale edit.

## Verification and rollout boundaries

See [validation instructions](./itsm-validation.md) for repeatable checks and the completed evidence.

The complete migration chain through `0007` is exercised in disposable PostgreSQL and a real local Supabase stack. Migrations `0004`–`0007` were also applied to the connected hosted database for the 28 September release; all eight migration hashes and the resulting functions, triggers, permissions and existing record counts were verified. The release report records the published revision and live checks. Future deployments must keep the migration and matching server/UI together; old clients without the required version token must be upgraded. This migration tightens direct incident writes, so integration clients need the same lifecycle contract.

Before rollout, validate against a staging copy: legacy pending/resolved records, old integration clients, requester/operator personas, cross-organization isolation, bridge operations, record activity, and backups/rollback. The repository uses both `supabase/migrations` and `drizzle/migrations`; follow the existing migration runner in the target environment rather than applying only the Supabase directory. Do not roll back by fabricating timestamps or resolution notes.

## Next delivery order

1. **Access administration and rollout:** review historical memberships/roles, resolve legacy approval inconsistencies, add controlled invitations and organization selection. The fixed-workspace access/privacy core is implemented and locally tested.
2. **Broader governed execution:** extend the implemented atomic approval/audit core to incident/problem/bridge links, configurable routing, standard-change templates and retention/offboarding. Core approval race and rollback checks are implemented.
3. **Service commitments:** policy configuration, response/resolution clocks, business calendars, approved pauses and durable escalations. Acceptance: replayable clock calculations and restart-safe escalation delivery.
4. **Product depth:** request/changes workbenches, catalog administration, CMDB dependency impact, knowledge review and accurate organization-level reports. Acceptance: complete end-to-end journeys with real data and persona checks.

This sequence is a prioritization judgment based on the inspected code and the benchmark capabilities, not a claim that all enterprise requirements have been delivered.
